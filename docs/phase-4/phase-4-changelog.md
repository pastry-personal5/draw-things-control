# Phase 4 changelog

Owner decisions, design decisions, and notable changes for
[Phase 4](README.md). Newest first.

## 2026-10-14

- **Change** [M09]: Job format version 2 is the only authoring format. Every live entry point (`validate-job`, queue submission, and the HTTP and MCP validate, preview, create, replace, and submit calls) refuses a version-1 or unversioned file at field `version`, with one message pointing to the new format; a `version: 2` file that still holds a removed version-1 key fails at that key and names where it lives now. `GET /v1/capabilities` gains `job_format` (the backends and pipelines, the knob names, and the Draw Things models that can take `seconds`). The four checked-in examples are converted and four more are added under `data/jobs/`, all validated by a test; the owner's own untracked version-1 files under `data/jobs/` are not rewritten and show as invalid until converted.
- **Design decision** [M09]: Supersede the earlier entry's "preserve already queued version-1 work through migration": a version-1 snapshot is not migrated or rewritten. It keeps its original text and runs, and resumes, on its existing path; the per-run accessors on `JobDefinition` derive any per-run view when it is read, and nothing derived is stored. A one-time rewrite would add a failure mode and no behavior the accessors do not already give. Only the snapshot reader passes `allow_version_1`.
- **Design decision** [M09]: Each version-2 run executes through a one-run view that its own adapter parsed and validated, so the command, finishing, and color code of both backends is reused unchanged and no second code path exists. Shared code never decides what one run does from a job-wide field: it asks `run_backend`, `run_needs_visual_input`, `run_checks_input`, and `job_for_run`. Alternatives rejected: rewriting both adapters around a new per-run interface (large, and nothing it would add is observable), and keeping the first run's job-wide fields as the whole job's (wrong as soon as a chain mixes backends).
- **Design decision** [M09]: Draw Things frame rates come from an authoritative table that ships empty. Nothing checked in states one and a rate observed in an output is not a rule, so every Draw Things `knobs.seconds` is refused with a pointer to `frames` until the owner characterizes a model and adds it with a research note ([frame-rate note](../research/draw-things-frame-rate.md)). An injected table proves the accepted path in tests. A base configuration's keys are never read as a rate.
- **Design decision** [M09]: A handoff that crosses a backend or settings-profile boundary is prepared by the consuming profile (a Draw Things `input_resize` plan or exact-size check; H3's center crop), as the job's first image is. Same-backend, same-profile handoffs pass as they are, as in version 1. The compiler checks the sizes it can know before anything runs; the executor checks the real file and stops the job before the dependent run when it cannot be used. A run's record names the earlier run and role its image came from (`input_run`, `input_role`) and the prepared copy (`resized_input`).
- **Design decision** [M09]: A version-2 execution has no single backend, mode, model, or base configuration. Its queue row, execution row, manifest, and `JobStarted` carry `mixed` for `backend` and `mode` when runs differ, an empty model and configuration, and the compiled plan under `backend_settings`; each run's own backend, pipeline, profile, and resolved knobs are recorded on its run. An independent `r2av` or `t2v` run after run 1 restarts the color anchor and first image.
- **Design decision** [M09]: A settings profile may serve several pipelines, so a setting that only some use is checked against the runs that select the profile: a positive H3 `color` policy needs an `i2av` run (`r2av` runs are measured only), and Draw Things `color` and `video_format` need a video run. A run's own `seconds` or `frames` replaces the default's temporal knob whichever it names, since the two are one choice. A run with no `seed` uses the execution seed and records its value with source `execution_seed`; a base configuration's own seed is ignored, with an INFO line. A Draw Things video run with no frame count anywhere leaves it to the CLI, as version 1 did, and records none.
- **Change** [M09]: The `runs` table gains `backend`, `pipeline`, `settings_profile`, `knobs`, `knob_sources`, `input_run`, and `input_role` (schema version 13), and `RunStarted` events and manifests carry them; they are null or empty for version-1 runs and for history imported before. The version-1 characterization goldens changed only by those new keys and columns. History import copies them from a manifest. The queue snapshot for a version-2 job is version 7: its `config_text` maps each Draw Things profile to its base-configuration text, and its stored plan is compared with the recompiled one on every read.

- **Owner decision** [M09]: Make generator timing a per-run knob. H3 runs accept `seconds` and derive both requested and effective frame counts; Draw Things video runs accept exact `frames` and may accept `seconds` only when the selected model's FPS is authoritatively resolvable before queueing. User-configured default prompt, profile, timing, seed, timeout, and `r2av` reference-pair values live together under one pipeline-scoped `defaults` key and can be overridden per run.
- **Design decision** [M09]: Introduce a version-2 authoring format with ordered `runs`, name-keyed catalogs, typed backend settings profiles, exact `(backend, pipeline)` default blocks, and an immutable compiled per-run plan. The `settings_profile` selector supersedes the earlier proposed per-run `backend_settings` selector so a selector cannot be confused with inline settings. Move H3 timing/seed and Draw Things frame-count/seed out of backend profiles, remove redundant run numbers and job-wide backend/mode/count/extension assumptions, preserve already queued version-1 work through migration, and record each effective value with its source.

- **Change**: Project-owned backend, media-tool, run-lock, and desktop child processes now cross a shared fork-free `posix_spawn`/clean-exec boundary. It preserves working directories, process-session supervision, pipes, timeouts, descriptor closing, and startup errors without copying live gRPC threads and poll descriptors through `fork`; the gRPC diagnostics no longer enter server or child output, and the exact process-output tests rejoin the parallel suite. The loopback launcher also drops its redundant `--allow-remote-bind`, and remote-token warnings now describe actual non-loopback binds only.

- **Owner decision** [M10]: Supersede the 2026-10-12 JSON-format choice: YAML is the canonical graph format for both the authenticated HTTP success response and explicit CLI export, with no graph JSON representation. Exports require `fc serve`; offline trace reads saved YAML. Exported graphs include recorded full local paths, cover job executions and only causal resume-point ancestors, and show unresolved gaps instead of inferring older links. They contain lineage and media facts, not duplicated seed, model, settings-profile, or timing controls. Saved files are read-only evidence; structural validation cannot establish that an edited file is authentic.
- **Design decision** [M10]: Place Milestone 10 after the unified per-run definitions in M09, link backends to runs, and make the reference, retained-copy, and actual-input identities needed for future graph edges durable in SQLite. Restrict YAML parsing to a bounded, unambiguous data subset and emit deterministic bytes. Imported manifest resume IDs must be preserved separately and verified or left unresolved before graph traversal.

- **Design decision** [M03]: Pass H3 the exact effective grid count with `--frames` alone. The checked-in CLI's `--seconds` parsing and mutually exclusive flags remain valid, but converting the aligned count back to seconds is unnecessary.
- **Change** [M03]: H3 queue snapshots now preserve the upward aligned timing of jobs submitted before the nearest-grid change. New H3 snapshots use version 6 so altered effective timing remains detectable.
- **Change** [M03]: H3 now snaps requested timing to the nearest supported `17n + 5` frame count and passes the resulting effective duration to the child. Requested and measured timing remain recorded separately.

- **Change** [M08]: Framecontrol now replaces Framechain throughout the active package, distribution, user-facing interfaces, MCP and gRPC identities, and current documentation. `fc` remains the sole command at version 3.0.0. The state store opens `state/framecontrol.db` and safely migrates either `state/framechain.db` or `state/dtc.db`; ambiguous files and held run locks require manual recovery.

- **Owner decision** [M07]: Increase the default parallel test worker count from four to eight; CI continues to select another safe count through `TEST_WORKERS` when needed. The baseline machine's full check completed in 29.65 seconds with eight workers.
- **Change** [M07]: `make check` now generates gRPC stubs before concurrent linting, type checking, and testing. The test suite runs through pytest-xdist with configurable workers and file-level distribution; the exact child-output test has its own clean pytest process after the parallel suite, avoiding a gRPC fork diagnostic contaminating its assertion. The initial four-worker measurement was 42.24 seconds for `make test` and 43.02 seconds for `make check`, against the 165-second serial-test baseline; `make test-profile` reports the configurable slowest tests.
- **Owner decision** [M07]: Require `make check` to complete in 60 seconds or less with a warm cache on the baseline machine, default to four configurable workers, and permit a maintained parallel-test dependency such as `pytest-xdist` when it produces the best verified result.
- **Design decision** [M07]: Keep the required `make check` coverage while reducing feedback time through isolated parallel test execution. Generated gRPC stubs remain a completed prerequisite before parallel consumers begin; direct `make -j check` is not the supported interface because the current peer prerequisites can race generated-file removal and readers.
- **Owner decision** [M08, M09]: Renumber the planned Framecontrol rename from M07 to M08 and the unified job definitions milestone from M08 to M09. Earlier changelog entries retain their original milestone labels.
- **Design decision** [M08]: Replace backend-specific run lists with one authoritative `runs` list. Each run selects its backend, pipeline, named prompt pair, and backend settings profile; mixed H3 and Draw Things chains use visual frame handoffs and do not require audio continuity.
- **Owner decision** [M08]: Use `draw-things` as the job backend identifier while retaining `draw-things-cli` for the executable, keep named top-level prompt-pair definitions, and select them from each run with `prompt_pair`.
- **Owner decision** [M06]: The Apple Silicon real mixed-chain review remains valuable release validation, but is not a Milestone 06 completion or exit gate.
- **Change** [M06]: Completed fingerprint-gated H3 color delivery, truthful-tag fallback, drift reporting, bounded optional correction, artifact-role persistence, output-limit enforcement, and front-end/history exposure. Synthetic coverage and `make check` pass; M06 is done.

## 2026-10-13

- **Change** [M06]: Added an H3 output storage planning limit for staged and retained MP4 copies and PNG handoffs, exposed through `api_limits.max_job_output_bytes` and enforced on submission and resume alongside the finishing time budget.

- **Change** [M06]: Enabled optional Apple Vision person, background, and skin drift measurements and bounded H3 region correction, with narrower skin caps and an explicit whole-frame fallback when segmentation is unavailable or insufficient. Synthetic H.264/AAC checks cover regional correction and fallback; real mixed-chain validation remains pending.

- **Change** [M06]: Added opt-in H3 whole-frame color correction with bounded Oklab lightness, contrast, chroma, hue, cast, and gamut-edge limits; it encodes a verified Rec.709 H.264 main output while copying native AAC. A successful correction retains separate raw and uncorrected MP4s; a failed optional correction keeps the verified uncorrected main output and raw child. Synthetic tests cover caps, cancellation, audio packet identity, artifact promotion, and fallback. Human mixed-chain validation remains pending.

- **Owner decision** [M06]: Adopt display-referred sRGB transfer and BT.709 primaries as an explicit engineering convention for the generated RGB of the characterized h3.c executable. This supersedes the transfer/primaries measurement gate in the earlier M06 entries for that fingerprint only; the convention is not a measured property of H3 or a promise for another executable.

- **Change** [M06]: Added fingerprint-gated, staged H3 BT.601-limited to BT.709-limited conversion with separate container, H.264 VUI, and stream declaration checks; verified AAC packet and timestamp copying, native-tag fallback, sRGB final-frame handoff, and per-run whole-frame drift facts. A positive correction request currently records a byte-identical raw child and an explicit skip warning while the correction path is being completed.

- **Change** [M06]: Verified a provisional BT.601/sRGB-to-Rec.709 finishing route with explicit bitstream/container tags, unchanged native AAC, and close RGB round trips on real PPM frames and saturated synthetic patches. The H3 source RGB transfer and primaries still need confirmation before automatic conversion or tagging.

- **Change** [M06]: Compared 124 same-run pre-encode H3 RGB PPM frames with their `r2av` MP4; sampled YUV errors verify the current limited-range BT.601 encode path. Transfer and primaries remain unproven, so automatic tagging and correction stay gated.

- **Change** [M06]: Recorded the owner-supplied real `r2av` child MP4, its matching h3.c fingerprint, absent bitstream/container color declarations, and portrait-size limited-range BT.601 encode-path evidence. Automatic tagging and correction remain gated on transfer/primaries and conversion verification.

- **Change** [M06]: A verified H3 MP4 now remains a successful run when optional handoff extraction fails, with a warning; a dependent `i2av` run stops before launch. Initial real `i2av` and synthetic encode-path color evidence is recorded in the H3 research note. Tagging and correction remain gated on full characterization, including an `r2av` child sample.
- **Owner decision** [M06]: Supersede the earlier M06 “untagged” fallback wording: retain the original H3 MP4 without adding tags when tagging or pixel interpretation is uncertain. Pre-existing conflicting child tags may remain if they cannot be removed safely, and the warning must identify them.
- **Owner decision** [M07]: Rename the product and app from Framechain to Framecontrol across the active package, interfaces, and documentation, superseding M04's name. Keep `fc` as the only command and version `3.0.0`; replace old public identities without aliases. Migrate `framechain.db` or `dtc.db` to `framecontrol.db` with verified backup and cleanup, preserve completed plans and past changelog entries, and name M10's planned schema `framecontrol-provenance-graph`.
- **Owner decision** [M06]: If the H3 child MP4 already contains conflicting color tags that cannot be removed safely, retain the original MP4 and warn explicitly about those tags rather than fail the run or re-encode solely to remove them.
- **Owner decision** [M06]: If conversion to the preferred Rec.709 delivery fails but the original H3 pixels are understood and the MP4 verifies, keep the original unconverted MP4 with a warning rather than fail the run.
- **Owner decision** [M06]: H3 correction defaults to whole-frame processing (`regions: false`). If optional drift measurement fails after the MP4 verifies, the run succeeds with a warning and reports measurement as unavailable.
- **Owner decision** [M06]: If the video pixels' color interpretation cannot be established, let that generated run succeed untagged with a warning, skip correction, and omit any handoff that would be unsafe. A dependent `i2av` run must not start without a verified handoff.
- **Owner decision** [M06]: When correction succeeds, the corrected MP4 is the main output shown in history and returned by the API; retain the uncorrected delivery MP4 and byte-identical H3 child MP4 separately.
- **Owner decision** [M06]: Retain both corrected and uncorrected MP4s and always retain a byte-identical H3 child MP4 for a correcting run. If color tagging cannot be verified, keep the run's MP4 untagged and report a warning instead of failing solely because of the tag.
- **Design decision** [M06]: Require real H3 `i2av` and `r2av` color characterization before selecting output tags. Keep a byte-identical child artifact for correcting runs, preserve AAC in corrected MP4s, derive corrected handoffs from the verified encode, and reset color anchors when an `r2av` run breaks an `i2av` segment. A failed optional correction falls back to a verified uncorrected handoff; cancellation does not.
- **Change** [M05]: Resume now checks a handoff only when the next H3 run uses `i2av`, including chains that began with `r2av`. Reference snapshots are opened beneath the configured input root without following links, copied within a 600-second submission limit, and verified only for pairs needed by unfinished runs; a missing descriptor cannot fall back to a live source. Retention gives unpublished submissions one hour before removing unreferenced copies. H3 preflight reads checkpoint counts and the `Metal 4` yes/no value from `--info`.
- **Owner decision** [M05, M06]: Defer H3 color characterization, tagging, and pixel conversion from M05 to M06. The sandbox's retry from the H3 checkout directory still reports no Metal device, so M05 will leave color handling unchanged.
- **Owner decision** [M05]: Configure reference snapshot byte caps as `api_limits.max_reference_file_bytes` and `api_limits.max_reference_bytes`, with factory defaults of 4 GiB per file and 32 GiB total per job.

- **Design decision** [M05]: Freeze Ref2VA assets at queue submission so queued and resumed runs consume the same verified copies; retain those copies for the resume chain. Match the checked-in H3 validator's 1–3 denoiser-reuse range, row-FC2 hardware and BF16-MLP exclusions, reference audio counting and duration rules, and record an executable fingerprint at claim for resume checks. Milestone 10 will project graph edges from M05's recorded input identities.
- **Design decision** [M05]: Specify exact h3.c CLI spellings for every render control, expose `int8_row_fc2` as `--use-int8-row-fc2`, and reject its conflict with `ssd_streaming`. Also reject simultaneous active `denoise_reuse` and `core_reuse` controls so resolved settings cannot construct an argv rejected by h3.c.
- **Owner decision** [M05, M06]: Tag every generated H3 video, including Ref2VA (`r2av`) output, with color metadata consistent with its encoded pixels. Plan opt-in, bounded H3 `i2av` color correction and drift reporting in M06; leave correction off by default and preserve raw generated outputs.
- **Design decision** [M05]: H3 rendering controls are modeled as a closed, resolved `backend_settings` contract instead of arbitrary CLI arguments. This exposes render-size, performance, memory, numerical-compatibility, and reference-image sizing choices while retaining reproducible snapshots, redacted commands, and field-specific validation.
- **Design decision** [M05]: Add an H3 detailed-run pipeline that mixes first-frame `i2av` and Ref2VA `r2av` runs. h3.c rejects reference inputs combined with first/last-frame anchors, so each `r2av` run selects its own ordered named reference pair while an `i2av` run alone consumes its predecessor's verified final frame. References are verified and copied into an execution-owned snapshot before execution, preserving the queued input set for audit and resume.
- **Change** [M04]: Legacy database migration now escapes project paths as SQLite file URIs, preserving history when a directory name contains URI punctuation such as `?` or `#`.
- **Owner decision** [M04]: Rename the product and app to Framechain, install only `fc` and `framechain`, and keep version `3.0.0`. MCP, caller-header, and gRPC identities change without aliases.
- **Change** [M04]: State now opens `state/framechain.db`. An existing `state/dtc.db`, including committed WAL data, is copied through SQLite backup, verified, and removed only after a safe migration; conflicting files or a held run lock require recovery before startup.
- **Owner decision** [M10]: Move the graph-based metadata milestone from M04 to M10; the milestone document and Phase 4 plan now use M10.
- **Change**: The API creates job files and replacement backups with private permissions. The server refuses linked, non-regular, or malformed token files and reads an existing token from one checked file descriptor.

## 2026-10-12

- **Change** [M03]: H3 is an installed `i2av` backend with a closed job schema, project-owned executable and model paths, first-frame normalization, controlled media-tool environment, staged MP4 promotion, verified final-frame handoffs, and H.264/AAC media validation. Its safe requested/effective timing settings are kept with queue snapshots and run records; local model snapshots are an installation dependency and are rechecked when work starts or resumes.

- **Design decision** [M03]: H3 outputs are generated into a unique sibling staging MP4, then strictly probed, decoded, and atomically promoted before they can be recorded or used as a handoff. The H3 child receives a controlled media-tool environment: inherited `H3_FFMPEG` and `H3_FFPROBE` overrides are rejected, and the resolved FFmpeg/FFprobe pair is placed first on its `PATH`. This prevents partial output and tool-selection drift across H3, preflight, and finishing.
- **Owner decision** [M04]: The graph is a DTC-owned JSON format, available through a read API and an explicit JSON export. The file is produced on request rather than after every execution.
- **Design decision** [M04]: Project a versioned provenance graph from a consistent read of execution history, then use the same schema for the API, CLI export, and offline trace. This avoids a second mutable graph store and event/file synchronization. Imported resume IDs must be remapped or left unresolved, because blindly treating an old manifest ID as a local execution ID could create false provenance.
- **Owner decision** [M03]: The final real H3 first-frame/MP4 acceptance run is performed by a human on the Apple Silicon host; automated tests use fake process and media tools because the Codex execution sandbox does not expose Metal.
- **Owner decision** [M03]: H3's accepted requested duration is 1–15 seconds, inclusive, before the backend applies the CLI's temporal alignment. This supersedes the 4–15-second duration decision below.
- **Owner decision** [M03]: H3's first input and every chain handoff normalize to the requested size by centered crop, rather than padding or stretching.
- **Owner decision** [M03]: H3's accepted requested duration is 4–15 seconds, inclusive, before the backend applies the CLI's temporal alignment.
- **Design decision** [M03]: Jobs require both temporal values and reject disagreement at 24 fps, but H3 commands pass only `--seconds`, because the checked-in CLI rejects `--seconds` and `--frames` together. Version 1 exposes no H3 performance controls.
- **Owner decision** [M03]: An H3 job supplies both `frames` and `seconds`; their requested values must agree at H3's fixed 24 fps before H3 applies its own supported-frame rounding. Requested, effective, and measured temporal values remain distinct in records.
- **Design decision** [M03]: H3 installation paths are project-owned and never job settings; its queue snapshot deliberately captures validated job state but not mutable model weights. H3 uses a closed `backend_settings` schema, normalizes every first-frame handoff under its own media policy, and a run succeeds only after FFprobe verifies and records both required video and audio streams.
- **Change** [M02]: The backend now prepares its own finishing context and safe settings summary; the shared chain no longer computes Draw Things color anchors. Version-3 queue snapshots verify resolved settings while version 1 and 2 remain readable, and the test backend exercises snapshot recovery. H.264 color correction can fall back to `libx264` when VideoToolbox cannot encode.
- **Change** [M02]: Jobs now name a backend (default `draw-things-cli`), validate backend settings through an adapter, and run backend-prepared commands through the shared chain. Queue snapshots, manifests, execution records, API responses, and resume keep that identity; older records read as Draw Things. A test-only backend checks the second implementation path, while H3 remains unavailable until Milestone 03.
- **Owner decision** [M02, M03]: Jobs use `backend` and `backend_settings`; Milestone 02 ships the Draw Things adapter and proves the interface with a test-only fake backend. H3 arrives in Milestone 03 and rejects `color` initially, until its color checks and correction have a backend-specific design.
- **Design decision** [M02]: The backend owns validation, command preparation, and output finishing; the shared executor owns the chain and supervision. A versioned queue snapshot and explicit backend fields in queue and execution rows preserve identity through recovery and resume; older records default to Draw Things.
- **Owner decision** [M02, M03, M04]: Phase 4 adds a multiple-backend refactor before h3.c support. H3 is the `i2av` backend, uses `--first-frame` for chain handoff and the repo-local `contrib/backends/h3.c/h3` executable, and is available through all existing front ends. Graph-based metadata remains a later milestone.
- **Design decision** [M02, M03]: Keep existing jobs on `draw-things-cli` by default, make backend identity durable for queue and resume, and scope the first H3 integration to first-frame-conditioned MP4 output with generated audio. H3 reference modes use different conditioning and are outside this milestone.
- **Change** [M01]: Milestone 01 is done. Its contextual shortcut help and focus-sensitive status-line hint are covered for the Jobs list, Queue list, Execution History list, and Execution detail; `make check` passes.
