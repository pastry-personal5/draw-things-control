# Milestone 06: H3 video color tags and correction

**Phase:** [Phase 4](README.md)
**Status:** done
**Depends on:** [Milestone 03](milestone-03-h3-i2av.md)'s H3 `i2av` output, finishing and handoff contract, and [Milestone 05](milestone-05-h3-r2av.md)'s mixed `i2av`/`r2av` pipeline.

## Goal

Make H3-generated MP4 color interpretation explicit and give `i2av` jobs optional, bounded controls for measuring and correcting color drift across chained runs.

## Scope

In scope:

- Characterize H3's encoded pixel range, matrix, transfer, and primaries, then attempt truthful tags on every generated MP4. If a tag cannot be verified, retain the original MP4 without newly added tags and report a warning, including any conflicting tags the child already carried. The preferred delivery target is SDR Rec.709: BT.709 primaries, transfer, and matrix with limited/TV range, only if the child output already encodes that contract or a verified finishing conversion produces it.
- Add H3 color drift measurement and opt-in color-correction controls for the existing `i2av` job contract. Keep the default correction off so jobs without color settings retain their current image-generation behavior.
- Always preserve a byte-identical copy of the H3 child output for a positively correcting run. Retain both the uncorrected delivery MP4 and a corrected MP4. When correction succeeds, the corrected MP4 is the main output in history and API responses, and the next `i2av` handoff comes from that verified copy. If correction fails, the uncorrected delivery MP4 is the main output.
- Persist validated policy and per-run results through queue snapshots, resume, execution settings, media checks, manifests, API/MCP, and CLI/TUI history as appropriate.

Out of scope:

- Adding color-correction settings to Ref2VA or changing Milestone 05's `r2av` input behavior. M06 attempts truthful tags on all H3-generated videos and reports a warning when it cannot verify them.
- Changing H3 inference prompts, model weights, or native audio content to compensate for color drift. A corrected MP4 must preserve native AAC samples and synchronization.
- Automatically correcting existing outputs or rewriting historic MP4s.
- Reusing Draw Things' pixel assumptions, sRGB transfer tag, half-level restoration, ProRes handling, or video-only correction encoder as H3 behavior without verifying each assumption. Share only backend-neutral policy, reporting, or media primitives that preserve H3's audiovisual contract.

## Color contract

- The owner has adopted display-referred sRGB transfer and BT.709 primaries as an explicit engineering convention for generated RGB from the characterized h3.c executable SHA-256 `79d4386f8f0825992f2204c643554fbba7c9c44fd7bfe54f1c6b2ba22308be9f`. Same-run `r2av` PPM-to-MP4 measurements establish its limited-range BT.601 encode path; transfer and primaries remain an assumption. The finisher must gate this convention on that fingerprint and revalidate source and delivery declarations. A future executable or conflicting child declaration has unknown pixel interpretation until separately characterized. This owner decision supersedes the stricter transfer/primaries measurement gate in the following evidence requirement for this fingerprint only.
- A human on the Apple Silicon host supplies representative unmodified H3 child MP4s from `i2av` and `r2av`, including dark and saturated frames. Record the h3.c executable fingerprint, FFmpeg/FFprobe versions, encode settings, source-image profile, and bitstream, stream, and container color facts in [H3 research](../research/h3-c.md). Compare decoded frames under candidate range and matrix interpretations; neither a missing tag nor a plausible player rendering proves a color contract. Do not enable automatic tagging until this characterization is complete. Recheck the assumption when the executable fingerprint changes.
- Keep the job policy in the existing top-level `color` block. H3 accepts a backend-owned closed schema: `anchor` (`none`, `previous`, `first`, `blend`), `strength` (finite 0–1), `first_weight` (finite 0–1), `reanchor` (`prompt_pair`, `never`), and `regions` (boolean). Omission resolves to `anchor: none`. For `none`, reject all dependent keys; for `previous`, allow `strength` and `regions`; for `first`, also allow `reanchor`; for `blend`, allow all keys. Reject irrelevant and Draw Things-only keys with field-specific errors. Use applicable defaults `strength: 1`, `first_weight: 0.25`, and `reanchor: prompt_pair`. Default `regions: false` for H3; enabled regions follow a verified whole-frame fallback if Apple Vision is unavailable. Draw Things parsing and defaults do not change.
- `anchor: none` measures without correction. `strength: 0` is a measured identity and creates no corrected copy. At positive strength, `previous` corrects toward that `i2av` run's prepared input; `first` also pulls toward the first input of the current contiguous `i2av` segment; `blend` applies `first_weight` of that extra anchor pull. With `reanchor: prompt_pair`, a changed prompt pair moves the segment anchor to the current input; `never` keeps its first input. Persist the effective anchor identity and re-anchoring reason per run.
- An `r2av` run has no frame input and is never corrected. It ends the current `i2av` color-anchor segment. A later `i2av` run uses its verified `r2av` handoff as both its input and the start of a new segment; no anchor crosses the `r2av` boundary. An all-`i2av` job retains one segment unless prompt-pair re-anchoring moves its anchor.
- Every H3 run attempts to measure first-to-last frame drift, even if no next run needs a handoff. `i2av` also compares its prepared input with frame 0 and its segment anchor with the last frame. For `r2av`, record input and anchor comparisons as unavailable with a reason; a reference is not a first-frame input. A failed drift check records a warning and unavailable facts, never fabricated zero drift, without invalidating an otherwise verified run.
- Before tagging, establish the actual encoded range and color transform from H3 output and the FFmpeg finishing path. If the preferred SDR Rec.709 target is not truthful, attempt a staged video-pixel conversion that preserves native AAC samples and timing, or document a different verified SDR delivery contract. If conversion fails but the original MP4 verifies and its pixels are understood, deliver it in its native color with a warning and truthful native tags where possible; otherwise keep the original MP4 and warn. Never newly label full-range samples as limited-range. The sRGB PNG handoff is a color-managed decode from the verified video interpretation; it does not imply that the MP4 has an sRGB transfer.
- The existing MP4 tagger writes an sRGB transfer code and leaves an existing `colr` box untouched. Extend or add an H3-specific tagging path that takes characterized primaries, transfer, matrix, and range; checks bitstream and container declarations; and handles absent, existing, and conflicting tags. Metadata-only tagging must preserve encoded video/audio payloads and timestamps. On failed tag write or verification, discard the staged tagging result, retain the original MP4, and warn; do not fail solely because of tagging. Never add a declaration known to contradict the pixels. If the child already contains conflicting tags that cannot be removed safely, retain it unchanged and warn explicitly that those tags remain; do not re-encode solely to remove them.
- Correction applies a bounded, versioned transform with documented lightness, contrast, chroma, hue, clipping, and region caps; establish numerical bounds during characterization before releasing the schema. It runs only when the original pixels' color interpretation is known, even if tags or preferred delivery conversion failed. Drift measurement, correction, and handoff extraction must explicitly decode under that known interpretation when retained child tags conflict; if they cannot do so safely, skip correction and omit the unsafe handoff. A corrected MP4 retains one H.264 video and one native AAC audio stream. Copy the original audio samples without modification, preserve their timing, attempt truthful color metadata for the corrected video, and reverify the full H3 media contract. Extract the corrected handoff from that verified encode so it matches the retained MP4. Tagging changes metadata only; successful delivery conversion and correction change pixels and are reported separately.
- Correction and media work have bounded per-run deadlines included in API worst-case duration estimates. Cancellation interrupts finishing before promotion; parking remains at the run boundary. An ordinary optional correction failure does not invalidate a successfully generated H3 run.

## Finishing and persistence

- Stage delivery conversion, tagging, drift measurement, optional correction, and any required handoff privately. Structural H3 media verification remains required. Tagging, preferred conversion, and drift measurement may warn and fall back. If pixel interpretation is unknown, keep the original verified MP4 without newly added tags, warn about any existing conflicting tags, skip correction, and omit an unsafe handoff. That run succeeds with a warning; a subsequent independent `r2av` run may continue, but a dependent `i2av` run stops before launch with a missing-safe-handoff dependency failure. Adapt the current H3 finisher and chain contract so an unavailable handoff does not retroactively mark the generated run as failed. Promote only verified artifacts, with cleanup or rollback on partial promotion. Check cancellation during bounded media work and before promotion.
- For a positive-strength correcting run, copy the child MP4 before any tagging or conversion and always retain that copy byte-identically as the raw artifact, even if correction is later skipped or fails. Name and reserve raw, uncorrected delivery, corrected, and handoff artifacts without collisions. Record each role, identify the corrected artifact as the main output when it succeeds, and record the actual next-run source. A structurally invalid MP4 fails the run. Tagging or preferred-conversion failure alone retains a verified original MP4 with a warning. No raw copy is required when correction is off.
- An optional correction failure discards incomplete correction artifacts and records its reason. If a later `i2av` run needs a handoff and the pixel interpretation is known, extract and verify the uncorrected frame from the delivered MP4. The run remains successful if its MP4 verifies. Cancellation is not an optional correction failure. If fallback extraction or verification fails, record no safe handoff and stop a dependent `i2av` run before launch. A drift-check failure alone does not block a valid handoff.
- Snapshot resolved H3 color policy and its version before queueing. Validate them on claim and resume without reading the current job file. Include mandatory verification, any delivery conversion, drift measurement, correction, and fallback extraction in API worst-case duration and storage limits without double-counting shared decoding. Expose safe basenames or artifact roles, never machine paths. Resume checks a saved corrected or fallback handoff only when the next run is `i2av`; it never reconstructs one from an unverified MP4 or reapplies a changed policy to a completed run.

## Acceptance criteria

- New H3 MP4 outputs have explicit color tags consistent with their encoded samples when tagging succeeds. At the SDR Rec.709 target, FFprobe reports BT.709 primaries, transfer, matrix, and verified range; an alternative documented SDR delivery requires equivalent evidence and tests. If tagging or its verification fails, the original verified MP4 is retained without newly added tags and with a warning that identifies any conflicting child tags. If preferred conversion fails, a structurally verified original MP4 is delivered with a warning and truthful native tags where possible. Any produced handoff agrees with the characterized pixels.
- Milestone 06 applies the generated-video tagging contract to both `i2av` and `r2av` runs, including an `r2av` run whose output is handed to a later `i2av` run.
- H3 color correction is opt-in and defaults to whole-frame processing. Existing H3 jobs without `color` keep the same generated media samples and safe handoff semantics apart from truthful metadata tags or a successful, documented delivery conversion. `strength: 0` creates no corrected copy.
- Every H3 run reports within-run drift or an explicit measurement warning. `i2av` reports input and segment-anchor comparisons where available; `r2av` never invents a first-frame input. A positively corrected `i2av` run retains a byte-identical raw child MP4, an uncorrected delivery MP4, and a verified corrected MP4 with unchanged native AAC samples. The corrected MP4 is the main output; its next-run handoff is extracted from it. If correction fails, the uncorrected delivery MP4 becomes the main output.
- Invalid or unsupported H3 color settings fail during job validation with field-specific errors. Resolved versioned settings survive queueing and resume; mixed chains reset anchors at `r2av` boundaries, and correction outcomes are visible in execution history.
- A failed optional correction leaves the generated run successful and reports a warning. With known pixel interpretation, it supplies a verified uncorrected handoff when a later `i2av` run needs one. Tagging or preferred-conversion failure alone leaves a structurally valid original MP4 and warning, even if conflicting child tags cannot be removed safely. Unknown pixel interpretation skips correction and unsafe handoff but does not fail the generated run; any dependent `i2av` run stops before launch, while independent `r2av` work may continue. Drift-measurement failure warns and reports unavailable facts. Structurally invalid media fails the run; cancellation interrupts rather than falling back; no partial artifact can seed resume.
- Draw Things color behavior is unchanged, and no H3 path invokes Draw Things-only half-level restoration, ProRes handling, or implicit color correction.
- `make check` passes when implementation lands; a human validates a real mixed H3 chain, audio, tags, decoded colors, and handoffs on the Apple Silicon host.

## As built

M06 implements fingerprint-gated H3 color interpretation, staged BT.601-limited to Rec.709-limited delivery conversion, verified metadata-only native tagging fallback, and warning-based retention when interpretation or tagging is unsafe. It records drift for every H3 run and offers bounded, opt-in `i2av` correction with byte-identical raw, uncorrected delivery, corrected-main, and verified-handoff artifact roles. Queue snapshots, resume, manifests, API/MCP, CLI/TUI history, output limits, and user-facing documentation retain the resolved policy and safe results.

Automated coverage includes synthetic H.264/AAC media, native packet/timestamp identity, declarations, conversion and tagging fallbacks, correction caps and artifact promotion, mixed-pipeline anchors, and cancellation. `make check` passed on 2026-10-14 (1,370 tests). The Apple Silicon mixed-chain review documented in the H3 research note remains valuable release validation, but is not a milestone completion gate by owner decision.
