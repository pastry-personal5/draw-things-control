# Milestone 20: Graph-based metadata

**Phase:** [Phase 4](README.md)
**Status:** planned
**Depends on:** [Milestone 02](milestone-02-multiple-backends.md)'s durable backend records, [Milestone 03](milestone-03-h3-i2av.md)'s audio/video facts, [Milestone 05](milestone-05-h3-r2av.md)'s reference snapshots, [Milestone 06](milestone-06-h3-color.md)'s artifact roles, and [Milestone 09](milestone-09-job-definition.md)'s per-run backend and pipeline records. Implement after Milestone 09; include older Draw Things and H3 history to the extent its facts were recorded.

## Goal

Export and read trustworthy provenance for a job execution. Starting from an output, a person or tool can follow its recorded producer, actual inputs and handoffs, earlier successful runs across resumes, the immutable job snapshot, and each run's backend. Missing evidence remains visible instead of becoming a guessed link.

## Scope

In scope:

- A Framecontrol-owned, versioned YAML graph document, a checked-in schema, deterministic export, and an offline reader.
- A graph projected on request from a consistent SQLite history snapshot. An authenticated HTTP read produces it; `fc history graph` saves or prints that response.
- `fc graph trace`, which reads a saved `.yaml` graph without `fc serve` or the original database and walks backward from an artifact.
- Successful and unsuccessful runs; original and prepared inputs; ordered H3 reference assets; generated outputs, retained raw/uncorrected/corrected copies, and verified video handoffs; missing or conflicting provenance.

Out of scope:

- Graph editing or importing a modified graph into Framecontrol, visual layout, a graph database, automatic sidecars, and replacing SQLite, manifests, or queue snapshots.
- One-off `generate` requests and jobs that have not started an execution.
- Reconstructing history by scanning media, parsing saved commands, or matching filenames or paths alone.
- Downloading media or embedding prompt text, commands, job YAML, credentials, file contents, or free-form media-check notes.
- Duplicating seed, model ID, settings profile, or effective timing controls from execution history. The graph records only the lineage and media facts needed to explain artifacts and their dependencies.

## Format decision

- YAML is the canonical graph format for both the HTTP success response and files. Use `.yaml`, UTF-8, one document, and `application/yaml` for the endpoint. The endpoint does not negotiate or produce graph JSON. Ordinary API errors retain the API's JSON error envelope.
- Use YAML for readable inspection beside YAML job definitions. Accept its extra parser complexity explicitly: version 1 data is limited to string-keyed mappings, sequences, strings, booleans, finite numbers, and null. Reject duplicate keys, aliases, anchors, merge keys, custom tags, multiple documents, implicit dates, cyclic or excessively nested values, and non-finite numbers. Quote strings whose plain spelling could change type. Parse only a bounded file with a restricted safe loader; never use a general object loader. The existing strict job-file YAML reader is a starting point, but its accepted syntax is broader than this graph contract.
- Define the data shape with a machine-readable JSON Schema vocabulary file encoded as YAML under `schemas/`, plus normative field, ID, edge, and trace rules and small examples in `docs/graph-format.md`. Validate the parsed data model and graph invariants, not YAML layout or comments. Emit one documented field order and sorted node, edge, and unresolved arrays with a final newline; two exports of unchanged history have identical bytes. Avoid export-time timestamps or filesystem-dependent values.
- A saved file is a self-contained account of what the store knew at export time. The offline reader checks structure and internal consistency but cannot prove the file was not edited; editing it forfeits its evidentiary trust. Version 1 does not promise a signature or media existence check.

## Graph contract

- The root mapping contains `schema: framecontrol-provenance-graph`, `version: 1`, persistent `store_id`, `root` (for example `execution:E0012`), `scope`, `complete`, `nodes`, `edges`, and `unresolved`. Generate the store ID once in a forward-only state migration, including for upgraded stores; preserve it across later openings and database copies. Node IDs are stable within that store, and `store_id` distinguishes two stores that both have an `E0012`.
- Node types are `job_snapshot`, `backend`, `execution`, `run`, and `artifact`. A job snapshot belongs to an execution's saved source text, with a digest of that exact text; never use the mutable live `J...` file. Do not embed the text. An imported execution without saved job text has no invented snapshot and has an unresolved definition reference. Backend nodes identify backend IDs; each run, rather than its whole execution, links to the backend and pipeline recorded by Milestone 09. Older execution-wide backend fields are used only where they unambiguously describe every recorded run.
- Run IDs contain execution ID and run number, for example `run:E0013:3`. Artifact IDs identify a recorded role and owner: for example `artifact:E0012:run:2:output`, `artifact:E0012:run:2:handoff`, or an execution-scoped reference pair, ordinal, and field. Paths are properties, never identities. Record full local paths where known and the role, snapshot digest/size where recorded, run outcome, measured video/audio facts, and whether an artifact was verified. Combine a recorded output directory and basename only when that location is unambiguous; an imported manifest's current directory is not proof of its original output location. A path records historical evidence, not current file existence; export never opens or hashes media.
- Directed edge types are `uses_job_snapshot` (execution to snapshot), `contains` (execution to run), `uses_backend` (run to backend), `consumes` (run to artifact), `produces` (run to artifact), `derived_from` (copy or handoff artifact to its recorded source artifact), `follows` (run to the verified direct producer of an input), and `resumes_from` (execution to its verified resume-point execution). Every edge joins nodes in the document and has a type-valid pair of endpoints. Run numbers show schedule order; `follows` expresses actual input dependency, so an independent `r2av` run never follows the previous run merely because it was next.
- Run 1's original image and any temporary prepared copy are separate artifacts. The run consumes the copy it actually received, when that is recorded; the copy derives from the original. A first `t2v` or independent `r2av` run has no invented frame input. An `r2av` run consumes its selected ordered, frozen reference copies, including separate audio fields, with recorded pair/ordinal/digest identities. A later image-conditioned run consumes the preceding verified output or extracted handoff actually used, even across backend and resume boundaries. A corrected output derives from its recorded uncorrected delivery, which derives from its raw child where recorded; a handoff derives from the delivered output that produced it. Do not invent intermediate copies or source relationships for old rows that lack them.
- Include a failed, timed-out, or interrupted run and only artifacts it actually recorded. A failed run cannot gain a successful handoff or a successor dependency merely from a reserved output name. If a successful MP4 has no safe handoff, retain its output artifact and mark the required next-run dependency unresolved if a dependent run was attempted. A missing optional artifact that was never produced does not itself make the graph incomplete.
- An edge across runs or executions requires a durable reference to the actual source artifact and the verified resume/run relationship. Path equality, consecutive run numbers, and an old manifest's `E...` number alone are insufficient. When a required source, definition, role, or identity is absent or inconsistent, retain known nodes and add an `unresolved` entry naming the source, intended relation, unavailable reference, and stable reason code. `complete` is true exactly when `unresolved` is empty; it means required provenance links are accounted for, not that media still exists. Scope-limited omitted parents are unresolved by design.
- A full graph for `E0013` contains that execution and only its causal resume-point ancestors needed to trace inputs, including runs within those executions. It does not add failed intermediate resume attempts that supplied no input or future descendants. Read all included rows in one SQLite read transaction. A deleted or pruned ancestor makes a later export partial; an existing saved YAML file remains unchanged.
- Readers reject unknown versions, malformed IDs, duplicate nodes/edges, dangling or type-invalid edges, causal cycles, invalid completeness, and schema violations with a field-specific error. Add version 1 optional properties only when old readers can safely ignore them; changed identity, edge meaning, or required structure needs version 2. No earlier graph format exists to migrate.

## Durable evidence and history repair

- Before implementing projection, audit what Milestones 05, 06, and 09 actually persist. Today H3 raw and uncorrected outputs are named in manifests and structured media-check facts, but not dedicated run columns; H3 reference descriptors live in queue snapshots; and backend identity is execution-wide in history recorded before Milestone 09. Milestone 09 now records on each run its `backend`, `pipeline`, `settings_profile`, resolved `knobs` with their sources, the earlier run and role its image came from (`input_run`, `input_role`), and the prepared copy it read (`resized_input`); a run with none of these predates it. Media-check writes can be skipped without stopping a run. Milestone 20 must make the remaining facts needed for future causal edges durable with the execution and run, through structured SQLite artifact/input records or equivalent fields, including each selected reference copy, original source where recorded, produced roles, and the actual handoff source file. A manifest or optional media check is not the sole live authority for a new graph edge.
- Backfill older history only from already stored, unambiguous structured facts. Preserve nulls and explicit unresolved entries where a role, source identity, pipeline, or copy relationship was not recorded. Existing manifests may inform a controlled import or repair, but projection never reads them as a second live source and never guesses from a path, command, or filename.
- `executions.resumes` currently stores a local-looking number copied directly from an imported manifest. An imported manifest may receive a different local execution number, so such a link is untrusted. In a forward migration, preserve the original external reference separately and invalidate unverified imported links before export can traverse them. For new imports, collect the batch's original IDs and assigned local IDs, then resolve only a unique matching ancestor in the same import provenance set; leave missing, duplicate, or conflicting IDs unresolved. A bounded, explicit repair of already imported manifests may restore a link only after matching the manifest to its stored execution and ancestor unambiguously; a missing or changed file leaves the external reference unresolved. Never link to a coincidentally equal local number.
- Use execution rows, per-run rows, and durable provenance facts in one consistent read. The artifact/input records serve history, not a second mutable graph store. History deletion and retention may remove rows; a missing target returns not found, and a missing ancestor is unresolved. Graph export itself does not prune, start a backend, acquire the run lock, or mutate history beyond a one-time schema migration on opening an older store.

## Production and consumption

- Add a shared `services` projection over `state` reads; put pure format validation and tracing below `services` within the existing dependency direction. Refuse a missing target, a one-off execution, and an actively running target until it is settled. Export terminal succeeded, failed, interrupted, and parked jobs. Distinguish a stale `running` row with no live runner using the existing history recovery convention, rather than requiring a run lock for graph reads.
- Add authenticated `GET /v1/executions/{id}/graph` with `scope=full` by default and `scope=execution` as a bounded fallback. On success return the canonical YAML bytes and `application/yaml`; on validation, size, state, or not-found errors use the normal API error shape. Bound the result to 10,000 nodes, 30,000 edges, and 8 MiB of emitted YAML; refuse an over-limit full graph rather than truncate it. The execution scope contains only the target and explicit unresolved parent references.
- Add `uv run fc history graph E0012 --output provenance.yaml` with the existing authenticated API client, server options, and `--scope full|execution`; `fc serve` is required. With no `--output`, print exactly the response YAML to stdout. With `--output`, refuse an existing destination by default, create a private temporary file in that directory, sync and atomically rename it, and keep local path-bearing exports private. Do not transform or reserialize the API response, so API and CLI bytes match.
- Add `uv run fc graph trace provenance.yaml --from artifact:E0012:run:2:output`. Read at most 8 MiB, parse and validate the entire graph before tracing, then print a deterministic backward traversal through derivation, producing runs, consumed artifacts, snapshots, and per-run backends. Show explicit unresolved stops and avoid resolving paths or consulting SQLite or the network. An absent `--from` artifact is a clear error. Handle shared sources without duplicate traversal or loops.
- Document the YAML contract, direct API use, CLI commands, full-path disclosure, edited-file trust limit, historical gaps, and retention effects in `docs/graph-format.md`, the user guide, and architecture when implementation lands. The TUI need not draw a graph in this milestone.

## Acceptance criteria

- API and CLI produce identical, deterministic version 1 YAML for a settled job. Run and artifact IDs stay unique across executions, and per-run backend and pipeline facts survive mixed chains.
- Starting at an output, offline trace follows only recorded causal inputs through producers, reference copies, job snapshots, and backends. Identical filenames or paths do not merge unrelated artifacts; independent `r2av` runs do not gain false predecessor edges.
- Failed or interrupted runs do not acquire successful handoffs. Missing old identities, pruned ancestors, and ambiguous imported IDs appear as reasoned unresolved references; trace stops without claiming missing evidence.
- A malformed, ambiguous, wrong-version, internally inconsistent, or oversized YAML file is refused with a useful error. The reader works without a server or database and never treats an edited file as verified by structure alone.
- Export does not modify settled history or write a sidecar unless requested. Full-path exposure and retention/deletion behavior are documented; existing Draw Things and H3 facts appear only where recorded. `make check` passes when the implementation lands.
