# Milestone 11: Job completion time estimation

**Phase:** [Phase 4](README.md)
**Status:** planned
**Depends on:** [Milestone 10](milestone-10-stage-timing.md) (done): its stage timeline, the `run_stages` and `run_timing` rows, and `RunOutput`'s `phase` and `offset`; and the existing cooldown policy.

## Goal

Replace the step-counter heuristics with one stage-aware forecast of the running job: the active run's seconds left, the job's seconds left, and a time-weighted share done, each with an honest range. The server computes the forecast once, and the TUI's work status, `fc queue add --wait`, `fc queue show`, the HTTP API, gRPC, and MCP show it. Its accuracy is measured by replaying recorded runs against the current estimator, not asserted.

## Evidence

**What the TUI does now** (`src/framecontrol/tui/estimate.py`). Before the first step reading, a run is estimated from the last successful run of any job. At the first reading it uses that run's time per step, and from the second on the mean pace since the first reading. A job's later runs are priced at the mean full time of its finished runs, and waits come from the cooldown policy. Every front end that wants progress would have to repeat this, because the server publishes only the last `n/N` it saw (`current_step`, `current_step_total`).

**Where [Milestone 10's data](milestone-10-stage-timing.md#evidence) shows that failing:**

1. H3 phases are read as one counter, so an early `1/1` or `50/50` marks the run as finishing, and Draw Things' `40 / 40`, which begins its last step, is read as the end. The estimator uses no knowledge of what stage is running.
2. Run 1 is priced from the latest run of any job. Run times span 654 to 2400 s across H3 settings, and the per-step time grows faster than the clip length, so an unrelated run misleads.
3. Later runs are priced at the mean of earlier ones, although identical settings varied by up to 31% from one run to the next.
4. A constant pace since the first reading is biased when the step time moves. In 7 of 8 Draw Things runs it rose 11% to 24% from the first quarter of the steps to the last, so at a quarter of the way the steps still to come are underestimated by roughly 15%.
5. The time after the last step is known only from a previous run's tail, so run 1 assumes none. That is the last step and 11 s of decode for Draw Things, and 66 to 142 s of decode and FFmpeg for H3. Framecontrol's own finishing is 1 to 2 s, or 38 to 46 s with H3 color correction, and is known only through an earlier run's full time.
6. A single time is shown with no sense of its uncertainty.
7. Progress reaches the TUI only as run output, which `/verbose low` does not send, so at low the bars have no step and the work status shows none.

## Approach

With the data one host produces in a retention window (a few runs a day), a small, regularized model with explicit uncertainty fits better than a flexible one. All of it is closed-form with `numpy`, which is already a dependency.

- **A run is a sum of stages.** The expected sequence is that of the newest complete run with the same signature, else of the same backend and pipeline: Framecontrol's own finishing depends on the knobs (a `correct` stage exists only with color correction). A stage still to come contributes a prediction and the current stage what is left of it. A stage the history has not seen, an `other` phase included, contributes nothing to the sum and widens the range by the pooled spread of that backend's non-iterative stages, and the basis names it.
- **Signature and features.** A run's signature is its backend, its pipeline, every workload key `TimingStarted` records except `seconds` (the effective `frames` carry it), and the `model` from its environment, with sorted keys and floats rounded to six places. For Draw Things that is the size, frames, steps, mode, guidance scale, strength, and shift, and for H3 the size, render size, frames, steps, references by kind, and the rendering knobs; the seed is already left out. The executable's size and modification time do not split a signature, since a rebuilt H3 would start every one over: the basis reports `build_changed` when the newest run it rests on was timed on another build. A live Draw Things row may hold no `frames`, and the loader then joins the run's measured `output_frames`. A row rebuilt from a log (fidelity `log`, from `fc timing import`) holds only the size, frames, steps, and recorded knobs it measured: no `mode`, no Draw Things guidance scale, strength, or shift, no H3 references or render settings, and an empty environment, so no `model`. It can never match a live row's signature, so it takes no part in tier 1 or in the spreads below, and it joins the fits of tiers 2 and 3 only over the features both fidelities hold. Only `complete` rows are used.
- **Iterative stages dominate** (denoise is 87% to 94% of an H3 run, sampling about 98% of a Draw Things run). Per-step time is modeled as `log t = f(workload) + u + noise`, one training row per complete run: its stage's mean step time, the first gap and any pause left out. `f` is a ridge-regularized least-squares fit on the logs of the retained history, over log pixels, log frames, pipeline, log of the reference count, and the knobs that vary in the data; the penalty is chosen at fit time by leave-one-execution-out error over a fixed grid and reported in the basis. A knob that never varies in the data is not extrapolated. `u` is this run's speed factor, `e + r`: `e` is shared by the runs of one execution (the machine's state) and `r` is the run's own. Their spreads come from same-signature live runs grouped by execution once three signatures have runs from two executions, and until then `u` has a prior spread of 0.10 in the log (the eight same-settings `r2av` runs spanned about ±8%) with `e`'s share of its variance, `rho`, at 0.5. Until live runs accumulate, the real history is log rows only, so those defaults stand.
- **Live update.** After each step of the active stage, `u` is updated by the normal-normal conjugate rule on the log ratio of measured to predicted step time, so the weight of history falls as steps accumulate. A step over three times the median of the steps so far (three times the predicted step before three exist) is a pause: it counts toward elapsed time, not toward the rate. A step still running past its prediction never leaves an `end_at` in the past: the step's remaining time is conditioned on its having lasted this long, so the range widens while the end moves. A per-backend within-stage trend, the slope of log step time against the step's place in the stage, is fitted from history and applied across the step index, so a rising step time is not extrapolated flat. The data shows why it must be fitted: Draw Things rose 11% to 24% in 7 of 8 runs while one fell, and H3's last third ran at 0.72 to 1.19 times its first with no consistent sign, so a slope is used only where its 95% interval over executions excludes zero. The first gap of an H3 denoise is a median 0.74 times a later one, so it is its own fitted coefficient and does not update `u` until that coefficient is known.
- **Other stages** (setup, decode and FFmpeg, Framecontrol finishing) use the same-signature median when there are 3 or more samples, else a log-linear fit on frames and pixels, with the residual spread as their variance.
- **Fallback tiers**, the first that qualifies: (1) the same signature with 3 or more complete runs from 2 or more executions; (2) a fit within one backend and pipeline, from 6 or more runs of 3 or more executions in which each kept feature varies; (3) a fit across one backend's pipelines with an indicator, on the same counts; and (4), with no history that qualifies for tiers 1 to 3, no number until the iterative stage has 2 readings, then a live-only forecast with the pooled spread. Tiers 2 and 3 fit on live rows when those meet the counts, and otherwise on live and log rows together over the features both hold. History of the other backend is never borrowed: a Draw Things step time says nothing about H3's. A forecast always carries its basis (tier, `fidelity`, run and execution counts, `build_changed`, unseen stages), and it is never invented. One run of unlike workload is not a tier, because it is hazard 2. The thresholds are provisional constants in `fit.py`, pinned by tests.
- **The job.** Remaining time is the active run's, plus each later run's prediction (its signature, computed before the run starts from the same description `TimingStarted` will record; `u` is shrunk toward this execution's measured one by `rho`, within one backend only, so a Draw Things run says nothing of the H3 run after it), plus Framecontrol's finishing per run, plus cooldown waits. A wait is the job's policy applied to the run's predicted child time, the sum of its child stages, which is `record.seconds`, what `JobExecutor` hands `wait_after`, and not the full run time. It widens its run's spread by the policy's slope (`1 + ratio` between the bounds in `auto`, else 1), and during a cooldown it is exact (`cooldown_until`). Run noise adds in quadrature and the shared `e` adds coherently. A resumed entry (`first_run > 1`) forecasts only the runs it will execute.
- **The range** is the 80% posterior predictive interval: a Student-t quantile with the fit's residual degrees of freedom (normal above 30), summed in seconds, with `low` never before now.
- **States.** In a cooldown or between runs `stage` and `run` are null and `job` counts what is left, the wait included. With a park reserved the job ends with the current run, so `job` repeats `run`'s figures (null in a cooldown, which a park ends) and the work status still says `parking` in place of the end. A cancel clears the forecast. A one-off `generate` has none, as it never had a step.
- **Where it runs.** The queue worker already observes every job event to keep its status. The forecaster sits beside that and is a pure function of `JobStarted`, `RunStarted`, `TimingStarted`, `StageStarted`, `StageFinished`, `RunOutput`, `RunFinished`, `CooldownStarted`, `CooldownEnded`, and `JobFinished`. The worker builds it for the entry after parsing the job and before the executor starts, so the fit (up to 200 ms) delays nothing already running and run 1 has a forecast at `RunStarted`.

Rejected: a constant pace (the present bias); the CLI's own percentage (its built-in prediction, not a measurement); an exponentially weighted pace (an arbitrary constant, no uncertainty); gradient boosting, neural, or full MCMC models (too few samples, and the conjugate update is exact for this model); any dependency beyond `numpy`; running the model in each front end (duplicated logic, and a golden test just to keep the copies equal); and borrowing the other backend's history for a first number.

## The published forecast

The worker holds the latest forecast of the entry it runs and clears it when the entry is released, a cancel is accepted, or the job ends. Every surface carries one object, `forecast`, null when there is none:

| Field | Meaning |
|-------|---------|
| `as_of` | The server's clock, in epoch seconds, when it was made |
| `stage`, `stage_done`, `stage_total` | The active stage (null in a cooldown or between runs) and its units (null when it counts none) |
| `run`, `job` | Null, or `started_at`, `end_at`, `low`, `high` (epoch seconds, as `cooldown_until` is) and `floor` (0 to 1) |
| `basis` | `tier` (`signature`, `backend_fit`, `pipeline_fit`, `live_only`), `fidelity` (`live` or `pooled`), `runs`, `executions`, `build_changed`, `unseen` |

A front end shows `seconds_left = max(0, end_at - now)` and `progress = min(1, max(floor, (now - started_at) / (end_at - started_at)))`, which is `floor` when `end_at <= started_at`, from one function in `services/forecast_view.py`, with `now` its own wall clock. A forecast replayed from the backlog after a reconnect or a switch out of `/verbose low` is old but not wrong, since its times are absolute. A front end on another host assumes synchronized clocks, as the TUI already does for `cooldown_until`, and `GET /v1/queue/{id}` carries `seconds_left` computed on the server for a client that cannot. The server sets `floor` to the largest share it has published or would have shown at `as_of`, so the bar never moves back within a run or a job, a forecast that grows holds the bar still until the time catches up, and a client that attaches mid-run draws the same bar with no history. The text may change freely.

- **Publishing.** A forecast is published at a stage, run, or cooldown change, when a park is reserved or withdrawn (the job's figures depend on it), and, within a stage, whenever its units advanced, at most once every 2 s and at the stage's last reading, so a 243-frame FFmpeg counter or a 0.2 s H3 setup phase cannot flood the 2000-event backlog. One identical to the last in stage, units, park state, and ends (within 1 s) is not republished; a completed step therefore always shows. `forecast_updated` is a queue-family event sent through `QueueEventPublisher` (data: `queue_id` and the object), not a `JobEvent`, so the recorder and the job log never see it. It is not `run_output`, so it passes the `include_output` filter and `/verbose low` keeps its bars.
- **Snapshots.** The HTTP queue entry, the SSE watch, and gRPC's `QueueEntrySnapshot` carry `forecast`. The proto adds a nested `Forecast` message as field 14 and reserves 8 and 9 and the names `current_step` and `current_step_total`. A snapshot is sent when the forecast is republished and never because time passed. `GET /v1/queue/{id}` also adds `progress` and `seconds_left` to `run` and `job`, computed at the read by the same function, for HTTP clients and for MCP, which imports nothing from the package. Front ends on gRPC (the TUI, `fc queue add --wait`) import `services/forecast_view.py`.
- **MCP.** `forecast` is not in `ACTED_ON_FIELDS`, so a forecast never wakes a `get_queue_entry` wait, which promises to answer at a run's end; the final read carries it. The tool's description says forecast where it says step.

## Scope

In scope:

- The model in `jobs/timing/`: `features.py` (signature and feature vectors), `fit.py` (the fit and tiers), and `forecast.py` (the forecaster and `Forecast`). They import only `core` and `numpy`. In `services/`: `timing_history.py` (the loader), `forecast_publisher.py` (the worker-side publisher), `forecast_view.py` (the display arithmetic), and `timing_replay.py` (the replay harness).
- The live input: `RunOutput` drops `progress` and `percent` and gains `stage`, `done`, and `total`, set when the line is a stage reading with a counter (Draw Things' `done` is steps done, as `Reading` already holds it). `StageFinished` comes only when a stage ends and the store's marks are written then, so without this the forecast would have no per-step input once `progress` goes.
- The server's surfaces above. `current_step` and `current_step_total` are removed from all of them, with `WorkerStatus`'s step and `QueueWorker.current_step`.
- The display: the TUI's work status (the Job and Run bars and the details line), the run summary, and the Execution detail's stage list; `fc queue add --wait` and `fc queue show`.
- The replay harness and `fc timing replay`, with a frozen copy of the current estimator in `tests/` as a baseline.
- Removing the old estimate: the model in `tui/estimate.py` (`moment`, `wait_fraction`, and `last_succeeded` are display helpers and move into `tui/text/status.py`); `LiveRun`'s `progress`, `percent`, `first_step`, `last_step`, `past_run`, `reference_run`, `forget_progress`, and `_read_step`; `StepReading`, `PastRun`, `latest_past_run`, `TuiApp.read_past_run` and its reads in `tui/feed.py`, `progress_text`, and `FinishedRun`'s `full_seconds`, `tail_seconds`, and `steps`; `ProcessMessage.progress` and `percent` with `PROGRESS_PATTERN` and `PERCENT_PATTERN`; and `ExecutionRepository.latest_succeeded_run` and its test, which nothing else uses. `tests/tui/test_estimate.py` goes with its module.

Out of scope, by owner decision on 2026-10-15: a predicted start and end for queued entries. The forecast covers the running job only; queue-wide prediction can follow as its own milestone. Also out of scope: changing generation, recommending knobs, notifications, predicting failure, a thermal or GPU model, and modeling host load or the executable's build (measured, not modeled; see the decisions).

## Planned changes

1. **Baseline first.** Port the current estimator unchanged into `tests/timing/` and replay it on the retained runs before any estimator changes, recording its error and whether hazard 1 is real. The replay rebuilds the stream the old estimator read from the store. A Draw Things mark stores `n - 1` done, so the baseline is given `done + 1`, the counter the CLI printed. A phase without marks is one `N/N` reading at its end, which reproduces hazard 1. A GPU-path H3 run's steps are its `denoise enqueue` marks, so its stream is the old estimator's own, but `denoise N/N` is read once at the end, as it was written, so the baseline is a faithful port of the rule and not of every line. Little real evidence remains to replay (checked on 2026-10-16). Pruning deletes an execution's `.log` with its row, so the eight Draw Things runs of E0026 and E0027 go on 2026-10-19 and 2026-10-20, and E0048 to E0050 (one H3 run each, the first two of one job) go about 2026-10-30. The logs of E0028 to E0047, the `r2av` set included, were deleted with their output folders and cannot be imported, so those executions keep only `runs.seconds`. By the time this is built the Draw Things baseline is synthetic only, and H3's rests on three runs (see the decisions).
2. **Model and forecast.** `jobs/timing/` gains the features, the fit, the posterior update, and a `Forecast` (the object above, as a dataclass). It is a pure function of the events and the fitted model, and every failure to read a row (a corrupt marks column, an unknown phase) skips that row, logs it once, and counts it in the basis; only an unexpected exception yields no forecast.
3. **Planned runs.** The job forecast needs the workload of runs that have not started. `JobExecutor` gains `describe_run(job, number)`, which returns the workload and environment `TimingStarted` will carry, from the compiled plan's knobs, and `_timing_facts` uses it. A test checks that for each run of fixture jobs of both backends the described workload equals the recorded one, so a prediction's signature is the one its row later gets.
4. **Loader and publisher.** `services/timing_history.py` reads the `complete` rows of `run_timing` with their `run_stages`, joins `runs.output_*` where a live row lacks `frames`, and caches the fit by the newest complete run and the row count, since pruning changes the count. `forecast_publisher.py` feeds each event to the forecaster, applies the publishing rule, holds `floor`, and sets the worker's latest forecast and the `forecast_updated` event. An empty store, a corrupt row, an unknown phase, or a run with no history yields a forecast of a lower tier or no forecast, and never an exception in the worker or a front end.
5. **Server and API.** The snapshot's `current_step` and `current_step_total` are replaced by `forecast`, as above, in `server/entry_snapshot.py`, `GET /v1/queue/{id}`, the SSE watch, `QueueEntrySnapshot`, and the MCP tool description. There is no optional-field tolerance, and a client and a server are expected to be the same version.
6. **TUI and CLI.** The front ends render the forecast and hold no model. The Job and Run bars read, for example, `ends ~16:42 (16:31 to 16:58)` and the details line `denoise 12/30  23 min elapsed`; the range is shown when its half-width is over 3% of the time left, and `estimating` stays when there is no forecast. A stage shows as its name with spaces for underscores. The run summary shows the stage and units in place of `progress`, at every verbose level. The Execution detail lists each stage of the selected run with its units, time, and share: completed spans from the stages endpoint, plus the active stage from the forecast for a run in progress. The reseed in `tui/feed.py` reads the snapshot's `forecast` where it read the step. `fc queue add --wait` prints the stage, its units, and the run's and job's ends with each run's start and at most once a minute after, and `fc queue show` prints the same line for a running entry. New terms (forecast, stage) go in [ux-terms.md](../ux-terms.md), which keeps the bars in the work status and the footer's status line apart.
7. **Replay.** `fc timing replay [--backend] [--estimator constant-pace|last-signature|forecast]` reads a store read-only (`browse`, as the TUI's history does, with no server needed), feeds the retained runs through an estimator as a live stream, and prints the metrics below. `cli/timing_app.py` imports only `services/timing_replay.py`. The frozen current estimator is in `tests/`, not in the command; an opt-in test scores it on a real store named by `FRAMECONTROL_REPLAY_STATE`, so the owner-host comparison uses one metrics function for both.
8. **Documentation.** The user guide (what the bars and the range mean; the `/verbose low` row and the work status text, which no longer say step progress is missing), architecture (the new modules and `QueueWorker`'s status, which no longer lists `current_step`), the HTTP and MCP guide, the phase changelog, and `docs/research/time-estimation.md`, which [Milestone 10](milestone-10-stage-timing.md) created and this extends with the baseline, the replay results, the host validation, and host load against the fitted `u`.

## Evaluation

- **Checkpoints:** 5%, 10%, 25%, 50%, 75%, and 90% of each run's true duration (RunStarted to RunFinished) for the run's remaining time, and 10%, 25%, 50%, 75%, and 90% of the job's for the job's, a job being its runs and the waits between them.
- **Metrics:** the median and 90th-percentile absolute percentage error of the remaining time, its signed bias, the coverage of the 80% range, the time to the first number, and the number of times the displayed share moves back.
- **Cross-validation:** a fit never includes the execution it is scored on, because runs of one execution share a machine state. `fc timing replay` leaves one execution out. The CI set groups executions into 10 folds, scores a seeded sample of 40 runs per fold, and runs in at most 20 s of CPU.
- **Baselines:** the frozen current estimator, a constant-pace estimator, and "the last run of the same signature".
- **Two data sets, kept apart.** The first is synthetic: a seeded generator writes runs for both backends from the spreads recorded in [Milestone 10's evidence](milestone-10-stage-timing.md#evidence) (a log-linear step time in pixels and frames, a per-run speed factor, a rising step time for Draw Things and a flat one for H3, occasional long pauses, constant setup and tail stages), at least 2000 runs over at least 20 signatures, grouped into executions of 1 to 6 runs with their cooldowns. It also varies what the estimator does not assume, so coverage is not tested against its own model: a heavy-tailed run factor, drift between executions, one Draw Things run in eight with a falling step time, H3's short first gap, signatures held out of the history, and a rebuilt-executable shift. It runs in `make check` and tests the algorithm against a known truth. The second is the real history the owner's database holds when the milestone is validated. It is small (14 days by default) and changes under the test, so it is measured once, on the owner host, and reported with each cell's run count and a bootstrap interval; a cell with fewer than 8 runs is listed and not judged. Coverage is judged pooled over the checkpoints from 10% on.

## Acceptance criteria

CI, on the synthetic data set and fixed scenarios:

- On runs that have at least 3 other same-signature runs from at least 2 other executions, the median absolute error of the remaining time is at most 15% at 10% elapsed, 5% at 50%, and 10% at 90%. The 80% range covers the truth between 70% and 90% of the time at each checkpoint from 10% on.
- For the job's remaining time, the median absolute error is at most 15% at 10% of the job and 10% at 50% and 90%, and the 80% range covers the truth between 70% and 90% of the time at each checkpoint (provisional, like the run targets).
- Pooled over the data set, at every checkpoint where the frozen current estimator gives a number, the new median error is lower. For each backend, pipeline, and checkpoint cell it is never more than 2 percentage points higher. The displayed share never moves back within a run or a job, across republished forecasts and for a client that attaches mid-run.
- When the run's backend has history that qualifies for tier 1, 2, or 3, the first number appears no later than the frozen estimator's, and for a signature with 3 or more samples before the first step reading. With thinner history (under 3 same-signature runs and under 6 of the backend) the forecast waits for two readings by design, and the frozen estimator's t=0 number, which priced the run from one unlike run or from the other backend (hazard 2), is listed beside it with its error and not compared.
- Scenario tests with synthetic readings: an early H3 `tokenizer 1/1` or `text encoder 50/50` does not read as finishing; Draw Things' `40 / 40` does not read as the end; a pause counts toward elapsed time and not toward the rate; a step that outlasts its prediction leaves `end_at` in the future with a wider range; an unknown phase widens the range and is named in the basis; each fallback tier is chosen, and reported in the basis, for the history that qualifies for it, and the other backend's history never qualifies; a cooldown, a reserved park, a cancel, a resumed entry, and a one-off `generate` give the forecast stated above.
- A wait is predicted from the run's child time: a replayed job's predicted waits equal `wait_after` of the predicted child time.
- The fit of 500 complete runs (about 12,000 spans and 20,000 marks) takes at most 200 ms, and a forecast update at most 5 ms per event. Failure injection (an empty store, a corrupt row, an unknown phase, a run with no history) never raises into the worker or a front end. A replayed 243-frame H3 run publishes at most one forecast per 2 s of a stage plus one per stage change.
- One recorded event stream yields the same published forecast fields from the HTTP snapshot, the gRPC snapshot, and the MCP entry, a forecast does not wake an MCP wait, and the TUI and `fc queue add --wait` render a given forecast to the expected text, at `/verbose low` too. `tests/test_architecture.py` fails if `tui/`, `cli/`, or `mcp_server/` imports `jobs/timing/features.py`, `fit.py`, or `forecast.py`, or `services/timing_history.py` or `forecast_publisher.py`, so no front end can grow a second forecast.
- The version-1 and version-2 characterization goldens are regenerated, and the diff shows only `RunOutput`'s lost `progress` and `percent` and its new `stage`, `done`, and `total`. No removed name (`current_step`, `PROGRESS_PATTERN`, `StepReading`, `PastRun`) remains in `src/`.
- Layering holds, no dependency is added, and `make check` passes.

Owner host validation, recorded in `docs/research/time-estimation.md` and not blocking completion: the same accuracy targets measured on the real retained runs (error, coverage, and the comparison with the frozen estimator, with run counts and intervals), and one real Draw Things job and one real H3 job on the new forecast compared with the actual end, as Milestone 06 does.

## Decisions for the owner

- **Open: the real evidence is nearly gone.** Of the executions the evidence came from, only E0026 and E0027 (Draw Things) and the newer E0048 to E0050 (H3) still have a log, and `fc timing import` rebuilds timing from nothing else. The logs of E0028 to E0047 were deleted with their output folders, not by retention, so [Milestone 10's](milestone-10-stage-timing.md#evidence) "about 2026-10-26" for the H3 runs was wrong. E0026 and E0027 are pruned, log and rows together, on 2026-10-19 and 2026-10-20, and an import does not outlast its execution. Under the standing no-copy decision (see [Milestone 10](milestone-10-stage-timing.md#decisions-for-the-owner)) no baseline on real Draw Things runs is possible, and its validation waits for runs recorded on the new recorder. Reversing that decision for the eight runs' per-step marks is the owner's choice and has to be made before 2026-10-19. Imported rows are log rows, which cannot form a tier-1 signature, so the real tier-1 and spread measurements need live runs, and three imported H3 runs can check little beyond the recorder.
- **The server computes the forecast once** (owner decision, 2026-10-16). Front ends show the published end and range, and count down from the end. Rejected: each front end running the model on the stage events, which duplicates the logic and needs a golden test to keep the copies equal, although the TUI already needs `fc serve`.
- **Real accuracy is measured once, not gated** (follows from the 2026-10-16 decisions in [Milestone 10](milestone-10-stage-timing.md#decisions-for-the-owner)). Timing rows are pruned with their executions and the logs behind the evidence are not kept, so no real data set stays fixed enough to gate `make check`. The synthetic data set gates the algorithm, and the owner-host measurement checks it against reality.
- **The targets are provisional.** They come from the data's own spread: eight `r2av` runs of one size, frame count, and step count (E0040 run 1, E0041 to E0047) took 2055 to 2396 s, about ±8%, and the live rate removes most of the denoise share of that after a few steps. The job-level targets are set the same way and are the least grounded; the baseline run may revise either. If a first measurement shows a target unreachable, it changes only through a changelog entry that records the measurement, not silently.
- **A range, not only a time.** The spread between identical runs makes a single time look more certain than it is. Rejected: hiding the range (the old behavior), and always showing it (noise on a steady run).
- **`current_step` is removed, not repurposed** (owner decision, 2026-10-16: backward compatibility may be broken; this supersedes the 2026-10-15 decision to keep the names with a new meaning). The old value was wrong for H3, and an older client reading a stage's counter as a global one would be wrong in a new way, so the fields go and `forecast.stage`, `stage_done`, and `stage_total` replace them.
- **The current estimator's heuristics are removed from the product** in this milestone, with the generic progress parsing they read. A frozen copy, adapted to the replay stream, stays in `tests/` as the baseline, and the owner-host comparison with it runs as an opt-in test, not a command option.
- **Host load and the build are measured, not modeled** (design decision, 2026-10-16; [Milestone 10](milestone-10-stage-timing.md#decisions-for-the-owner) left the load question to this milestone). The research note reports how the run's start load average and a changed executable relate to the fitted `u`. Either enters the model only through a changelog entry that records that measurement, since a signature split by build would starve the top tier after every H3 rebuild.
- **Live readings ride on `RunOutput`; the forecast is a queue-family event** (design decision, 2026-10-16). Rejected: a `StageProgress` job event beside `RunOutput` (a second event per reading), publishing the share (it changes on every read, so every poll would send a snapshot), and a `JobEvent` `ForecastUpdated` (the recorder and job log would see it).
